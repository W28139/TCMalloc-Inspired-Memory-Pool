# CentralCache → ThreadCache 批量传输问题

## 问题概述

当前项目中 CentralCache 向 ThreadCache 分发内存块时，每次只传输 **1 块**，而非真正的 TCMalloc 那样**批量传输多块**。ThreadCache 中的相关代码（遍历链表、计数 `batchNum`）是为此预留的，但目前等于白跑。

## 当前实际行为

### 传输路径

```
ThreadCache::fetchFromCentralCache(index)
    │
    ▼
CentralCache::fetchRange(index)
    │
    ├── centralFreeList_ 有货？
    │   └── YES → 取链表头 1 块
    │            *reinterpret_cast<void**>(result) = nullptr  ← 断开，next 置空
    │            返回单块
    │
    └── NO → 从 PageCache 拿 Span，切成 blockNum 块
             *reinterpret_cast<void**>(result) = nullptr  ← 断开第一块，next 置空
             剩余块挂在 centralFreeList_（CentralCache 自己内部）
             返回单块
```

### 关键代码（CentralCache.cpp 两处断开）

```cpp
// 分支 A：从 PageCache 新切 Span 后（第 217-218 行）
*reinterpret_cast<void**>(result) = nullptr;     // 断开第一块
centralFreeList_[index].store(next, ...);         // 剩余块留在 CentralCache 自己手里

// 分支 B：从 centralFreeList_ 取现成块（第 114-116 行）
*reinterpret_cast<void**>(result) = nullptr;     // 断开第一块
centralFreeList_[index].store(next, ...);         // 剩余块留在 CentralCache 自己手里
```

### ThreadCache 侧（ThreadCache.cpp 第 71-96 行）

```cpp
void* ThreadCache::fetchFromCentralCache(size_t index)
{
    void* start = CentralCache::getInstance().fetchRange(index);
    // start = 单块，start->next 永远是 nullptr

    void* result = start;
    freeList_[index] = *reinterpret_cast<void**>(start);
    // ↑ 读出来永远是 nullptr，因为 CentralCache 已经断开了

    size_t batchNum = 0;
    void* current = start;
    while (current != nullptr)
    {
        batchNum++;                                    // 永远是 1
        current = *reinterpret_cast<void**>(current);  // 永远是 nullptr，立刻退出
    }
    freeListSize_[index] += batchNum;  // 永远是 += 1

    return result;
}
```

### 时序图（当前行为）

```
每次 allocate（ThreadCache 本地无缓存）都触发一次 CentralCache 调用：

  allocate #1 → fetchRange → [CentralCache 返回 1 块]
  allocate #2 → fetchRange → [CentralCache 返回 1 块]
  allocate #3 → fetchRange → [CentralCache 返回 1 块]
  ...

Cross-layer calls = N（N = 分配次数）
```

## 真正的 TCMalloc 行为

在 Google TCMalloc 中，`CentralFreeList::RemoveRange` 会一次返回 `batch_size` 个块（串成链表）。

### TCMalloc 的 batch_size 计算

```cpp
// tcmalloc/central_freelist.cc (简化)
static constexpr size_t kMaxObjectsToMove = 32;

int CentralFreeList::RemoveRange(void** start, void** end, int N) {
    // N = min(used_length, kMaxObjectsToMove)
    // 返回 N 个块组成的链表
    // *start = 链表头
    // *end   = 链表尾
    return N;  // 实际返回的块数
}
```

### 批量传输的时序图

```
  allocate #1 → fetchRange → [CentralCache 一次返回 8 块]
      ├→ 第 1 块返回给用户
      └→ 剩余 7 块挂入 ThreadCache.freeList_

  allocate #2 → 命中 ThreadCache 本地（无 CentralCache 调用！）
  allocate #3 → 命中 ThreadCache 本地
  ...
  allocate #8 → 命中 ThreadCache 本地
  allocate #9 → fetchRange → [CentralCache 再返回 8 块]
      ...

Cross-layer calls = N / batch_size（大幅减少）
```

## 修改方案

### 方案 A：修改 CentralCache::fetchRange 返回链表（推荐）

**改动位置 1**：CentralCache.cpp `fetchRange`，不再断开 `result` 与后续链表的连接。

```cpp
// === 修改前（分支 B 为例）===
void* next = *reinterpret_cast<void**>(result);
*reinterpret_cast<void**>(result) = nullptr;          // ← 删除这行
centralFreeList_[index].store(next, ...);

// === 修改后 ===
void* next = *reinterpret_cast<void**>(result);
// 不断开，result 仍然指向后续链表
// result → next → ... → nullptr
centralFreeList_[index].store(next, ...);  // 不对，next 也不能留在 CentralCache

// 正确的做法：直接取出整条链表
// 方案：从 centralFreeList_ 取出前 N 块（或全部），返回链表头
```

**更准确的思路**：`fetchRange` 从 `centralFreeList_` 取出一段子链表（前 N 个节点），断开第 N 个节点的 next，返回这段链表的头。N 可以是一个可配置的批量大小。

### 方案 B：使用配置化的批量大小

```cpp
// 新增常量
static const size_t BATCH_SIZE = 8;  // 每次向 ThreadCache 传输的块数

void* CentralCache::fetchRange(size_t index, size_t& outBatchSize)
{
    // ...获取锁...
    void* head = centralFreeList_[index].load(...);

    if (!head) {
        // 从 PageCache 申请新 Span，切分，链表头 = head
    }

    // 取前 BATCH_SIZE 个节点
    void* result = head;
    void* current = head;
    size_t count = 1;

    while (count < BATCH_SIZE && *reinterpret_cast<void**>(current) != nullptr) {
        current = *reinterpret_cast<void**>(current);
        count++;
    }

    // 断开：current 是第 BATCH_SIZE 个节点
    void* remaining = *reinterpret_cast<void**>(current);
    *reinterpret_cast<void**>(current) = nullptr;

    // 剩余放回 CentralCache
    centralFreeList_[index].store(remaining, ...);

    outBatchSize = count;
    return result;  // head → ... → current → nullptr（count 个节点）
}
```

**改动位置 2**：ThreadCache.cpp `fetchFromCentralCache`，利用返回的链表。

```cpp
void* ThreadCache::fetchFromCentralCache(size_t index)
{
    size_t batchSize = 0;
    void* start = CentralCache::getInstance().fetchRange(index, batchSize);

    if (!start) return nullptr;

    // 取链表头返回给用户
    void* result = start;

    // 剩余块挂入本地 freeList_
    freeList_[index] = *reinterpret_cast<void**>(start);
    //   ↑ 现在有值了！因为 CentralCache 返回了多个块串成的链表

    freeListSize_[index] += batchSize;  // 现在有意义了：> 1

    return result;
}
```

### 方案 C：在 ThreadCache 侧循环调用（最简单但不优雅）

不改 CentralCache，在 `fetchFromCentralCache` 中循环调用 `fetchRange` N 次，自己串成链表。缺点：每次循环都要加锁/解锁，批量优化的效果打了折扣。

## 影响评估

| 维度 | 当前行为（单块传输） | 改为批量传输后 |
|:---|:---|:---|
| ThreadCache ↔ CentralCache 调用频率 | 每次 allocate 1 次 | allocate / BATCH_SIZE 次 |
| 自旋锁竞争 | 频繁（每次 allocate 争夺一次） | 大幅减少 |
| CentralCache 链表遍历次数 | 每次取 1 块，链表操作频繁 | 每次取 BATCH_SIZE 块，均摊到每块的操作减少 |
| ThreadCache 命中率 | 不直接影响（由 deallocate 归还决定） | 批量获取后 immediate 命中率提升 |
| 代码复杂度 | 低 | 中（需处理链表截断） |

## 测试验证点

修改后需要验证：

1. **正确性**：批量传输后，每个块的地址正确、链表结构完整
2. **SpanTracker 计数**：从 CentralCache 取出 BATCH_SIZE 块后，`freeCount` 的扣减应与实际取走的块数一致
3. **内存泄漏**：所有块最终都能正确归还到 PageCache
4. **性能**：多线程场景下，`fetchRange` 的锁持有时间和调用频率对比
5. **边界情况**：
   - `centralFreeList_` 中块数 < BATCH_SIZE
   - `centralFreeList_` 中正好等于 BATCH_SIZE
   - `centralFreeList_` 为空需要新切 Span
