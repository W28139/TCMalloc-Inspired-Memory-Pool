# 压测报告：优化参数验证与环境漂移分析

## 类型

**性能验证 / 实验报告（2026-08-18）**

## 背景

优化 #14~#23 应用后，首次压测对比 2026-08-12 基线发现多线程场景"变差 15%"（6.14 vs 5.349 ms），触发系统性参数实验：

1. 单变量参数矩阵：BATCH_SIZE、归还阈值、自旋锁退避策略
2. 基线复现实验：stash 还原 7b8fa2c 代码复测
3. 环境因素排查：CPU 拓扑、调度固定、跨轮方差

## 环境

| 项 | 值 |
| :--- | :--- |
| 系统 | WSL2（Linux 6.6.87.2-microsoft-standard-WSL2） |
| CPU | Intel i7-14700HX，14 物理核 × SMT2 = 28 逻辑核 |
| 频率 | 实测 2.3 GHz（base；turbo 可达 5 GHz） |
| 编译 | g++ -O2 |
| 工具 | `bin/perf_test`，每组合 3~5 轮取中位数 |

## 实验方法

- **同轮配对**：压测程序同一进程内交替测 MemoryPool 与 new/delete，用 `MP/new` 比率抵消环境漂移
- **多轮中位数**：绝对时间波动大，单轮采样不可靠
- **基线复现**：`git stash` 源码后复测 7b8fa2c 版本，确认代码一致性与环境漂移
- **固定核对照**：`taskset -c 0,8,1,9` 将 4 线程钉在 4 个独立 P 核，验证调度因素

## 实验矩阵与数据（2026-08-18，同环境）

| 组合 | 多线程中位数 | MP/new 配对比率 | 单线程小对象 |
| :--- | :--- | :--- | :--- |
| **优化版（BATCH=32 + 阈值2048 + pause）** | **~6.13 ms** | **~0.74（最优）** | ~1.7 ms |
| 基线复测（8 + 256 + yield，全旧） | ~6.45 ms | ~0.81 | ~2.1 ms |
| BATCH=8 + 阈值2048 + pause | ~6.50 ms | ~0.81 | ~1.8 ms |
| BATCH=32 + 阈值256 + pause | ~6.35 ms | ~0.79 | ~1.8 ms |
| BATCH=32 + 阈值2048 + yield | ~6.54 ms | ~0.81 | ~1.8 ms |
| **BATCH=8 + 阈值256 + pause（完全还原）** | **~7.59 ms** | **~0.87（最差）** | ~1.8 ms |

注：单线程小对象优化版 ~1.7 ms vs 基线 ~2.1 ms，**-20% 真实收益**，且 8-12 基线 2.148 完全复现；混合大小场景各组合 ~2.2 ms 持平（8-12 基线 2.199）。

## 关键发现

### 1. "多线程变差 15%" 是跨日环境漂移的误判

- 8-12 基线多线程 5.349 ms 在今天**无法复现**：stash 还原的同代码复测为 ~6.45 ms
- 单线程场景两天完全吻合（2.148 vs ~2.1）→ **代码一致性确认**，漂移集中在多线程场景
- 同一份代码今天跨轮波动 **4.2 ~ 8.1 ms**，绝对时间的主导变量是环境而非代码

### 2. 漂移来自 host 侧，guest 内不可控

- `taskset` 固定 4 个独立 P 核后波动依旧（8.4 / 7.5 / 6.5 vs 自由调度 5.1 / 6.6 / 6.9）
- 排除 guest 内线程调度因素 → 归因 WSL2 之外的 host 侧：vCPU 抢占、CPU 频率（2.3 GHz base vs 5 GHz turbo）、内存带宽竞争
- 多线程场景更敏感的原因：长任务窗口（4×6-8 ms）被抢占概率高；桶锁自旋是纯 CPU 指令，对频率抖动最敏感，一次抢占放大所有等待线程的延迟

### 3. 参数验证：当前优化参数即最优，完全还原最差

| 假设 | 验证结果 |
| :--- | :--- |
| BATCH_SIZE 32 临界区过长 → 竞争放大 | ❌ BATCH=8 反而更慢（6.50），锁获取次数 ×4 的代价大于临界区收益 |
| 阈值 2048 本地缓存过多 | ❌ 阈值 256 无改善（6.35） |
| yield 退避优于 pause | ❌ yield 无改善（6.54），WSL2 下调度延迟大 |
| 完全还原（8+256） | ❌ **最差**（7.59），CentralCache 交互最频繁 |

机制：BATCH=32 使锁获取/释放次数降 4 倍，阈值 2048 使 returnRange 次数降 ~16 倍（每 size class 25000 次分配约 12 次 vs 98 次），ThreadCache↔CentralCache 交互最小化是竞争环境下收益的主要来源。与优化 #20、#22 的设计意图一致。

## 结论

1. **当前代码（BATCH=32 + 阈值 2048 + pause 指数退避）即最优参数组合，无需回退**，全矩阵配对比率 0.74 最优
2. 优化整体有效：单线程小对象 -20%，多线程与混合大小持平或略优
3. 8-12 的 5.349 ms 是当时环境下的单点采样，不是代码水平上限（优化版今天曾跑出 4.238 ms）

## 后续建议

- **压测方法论**：多轮取中位数 + 同轮 `MP/new` 配对比率；跨日绝对毫秒数不可直接比较；记录 CPU 频率与 host 负载
- **可选的进一步优化方向**（本次实验未实施）：桶锁竞争仍是多线程场景的主要开销（配对比率 0.74 → 理论下限 ~0.66 为 new/delete 的无锁 fast-path），可考虑按线程分桶、批量缓存抢占（如 tcmalloc 的 TransferCache 式批量缓冲）降低锁获取频率
