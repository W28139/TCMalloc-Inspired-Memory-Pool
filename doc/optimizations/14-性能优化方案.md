# 性能优化方案 v1.0

> 本文档只给方案，不实施。优先级：**先修正确性（P0），再做第一档，最后按需做第二/三档**。
> 正确性问题的完整分析见 `doc/review-2026-08-12.md`。

## 一、最新基线（2026-08-12）

环境：WSL2 (Linux 6.6.87.2-microsoft-standard-WSL2)，g++ -O2，`bin/perf_test` 单轮。

| 场景 | MemoryPool | new/delete | 差距 |
|:---|:---|:---|:---|
| 单线程小对象 50000 次 | 2.148 ms | 2.102 ms | ≈ 持平 |
| 4 线程 × 25000 次 | 5.349 ms | 8.060 ms | 快 33% |
| 单线程混合大小 100000 次 | 2.199 ms | 4.862 ms | 快 55% |

对比修复 #04（批量传输）前的基线（`00-压测基线.md`：慢 44% / 慢 16% / 快 84%），内存池已从全面落后变成多线程、混合大小领先。**但多线程优势仍偏小**——tcmalloc 风格的池在 4 线程下通常领先 2 倍以上，说明桶锁竞争和跨层交互仍是瓶颈。

## 二、瓶颈分析

1. **桶锁竞争**：`fetchRange`/`returnRange` 每次操作都 `test_and_set` + `clear`（`CentralCache.cpp:124`、`:320`），且 `yield()` 退避在争用时会立刻重试，加剧缓存行颠簸；
2. **跨层交互频率**：`BATCH_SIZE=8`（`CentralCache.h:136`）与 ThreadCache 归还阈值 256（`ThreadCache.cpp:113`）相比 tcmalloc 的批量 32 偏小，多线程下 CentralCache 是热点；
3. **fetchRange 分支 B 的 per-block 二分**：每取一块就调一次 `getSpanTracker`（`CentralCache.cpp:284-290`），批次内 8 块通常同属一个 Span，二分重复执行；
4. **缓存足迹**：ThreadCache 两个 32768 元素数组（`freeList_` + `freeListSize_` = 512KB）超出 L2，热路径数据访问分散。

## 三、第一档（推荐：改动小、风险低、收益最大）

### 1. 先修 P0-1 / P0-2（正确性前提）

- P0-1：`expandTrackerArray` 排序破坏索引语义 → 活跃 SpanTracker 被覆盖（永久泄漏 + 二分失效）
- P0-2：归还后 tracker 不失效 → 地址复用时二分误命中僵尸 tracker（UAF）

修复方法见 `doc/review-2026-08-12.md` 第五节。**性能优化必须建立在正确代码之上**，且 P0-2 修复（归还后 `spanAddr.store(nullptr)`）是下方第 5 项优化（tracker 复用）的安全前提。

### 2. BATCH_SIZE 8 → 32 ✅ 已实施（2026-08-18，见 `20-BATCH_SIZE提升到32.md`）

| 项 | 值 |
|:---|:---|
| 位置 | `CentralCache.h:136` |
| 改动 | `static const size_t BATCH_SIZE = 32;` |
| 原理 | 跨层调用次数和桶锁获取次数降 4 倍；tcmalloc 批量 32 是业界经验值 |
| 预期收益 | 多线程场景 15%~30% |
| 风险 | 每线程最多多缓存 24 块同大小块，内存占用略增（可忽略）；`freeListSize_` 上限变 256+32=288，仍远小于 uint16_t 上限 |

无需改其他代码——`fetchRange`/`fetchFromCentralCache` 都按 `BATCH_SIZE` 上限工作。

### 3. 自旋锁：yield → _mm_pause + 指数退避 ✅ 已实施（2026-08-18，见 `21-自旋锁yield改mm_pause指数退避.md`）

| 项 | 值 |
|:---|:---|
| 位置 | `CentralCache.cpp:124-127`、`:320-323`（两处相同的自旋循环） |
| 现状 | `while (test_and_set) std::this_thread::yield();` — yield 把线程让给调度器（微秒级），争用激烈时恢复后立即重试，缓存行在多个核间反复横跳 |
| 方案 | |

```cpp
// 替换 fetchRange / returnRange 中的自旋循环（两处）
for (int spin = 0; locks_[index].test_and_set(std::memory_order_acquire); ++spin)
{
    // 指数退避：pause 次数 1,2,4,...,64（上限），总退避时间从 ~10ns 到 ~几百 ns
    for (int i = 0; i < (1 << std::min(spin, 6)); ++i)
        _mm_pause();   // x86 PAUSE 指令：降低功耗 + 减少总线争用
}
```

| 项 | 值 |
|:---|:---|
| 头文件 | `#include <immintrin.h>`（x86/x86_64）；非 x86 平台用 `#if defined(__x86_64__)` 包住，退化回 yield |
| 预期收益 | 多线程争用场景 20%~40%（避免线程被调度器踢出再唤醒的微秒级延迟） |
| 风险 | 单线程路径无影响（第一次 test_and_set 失败即退出循环） |

### 4. ThreadCache 归还阈值 256 → 1024 ✅ 已实施（2026-08-18，见 `22-ThreadCache归还阈值提升到1024.md`）

| 项 | 值 |
|:---|:---|
| 位置 | `ThreadCache.cpp:113` |
| 改动 | `size_t threshold = 1024;` |
| 原理 | 归还频率降 4 倍，CentralCache 交互减少，配合 BATCH_SIZE=32 后每次归还量更大 |
| 预期收益 | 多线程场景 5%~15% |
| 风险 | 每线程同大小最多缓存 1024 块（如 256B 块 = 256KB/线程），内存占用上升；可接受 |

## 四、第二档（中等改动，热路径精细优化）

### 5. fetchRange 分支 B：批次内复用 SpanTracker（免 per-block 二分） ✅ 已实施（2026-08-18，见 `23-fetchRange批次内复用SpanTracker.md`）

| 项 | 值 |
|:---|:---|
| 位置 | `CentralCache.cpp:283-290` |
| 现状 | 批次内每块一次 `getSpanTracker`（O(log n) 二分 + 可能 O(64) 线性扫描），而链表连续块几乎总同属一个 Span（returnRange 整段插入、切分时顺序链接） |
| 方案 | |

```cpp
// 缓存当前 tracker：只有块越出当前 Span 区间才重新二分
SpanTracker* cur = nullptr;
void* current = result;
for (size_t i = 0; i < batchCount; ++i)
{
    if (!cur ||
        current < cur->spanAddr.load(std::memory_order_relaxed) ||
        current >= static_cast<char*>(cur->spanAddr.load(std::memory_order_relaxed)) +
                     cur->numPages.load(std::memory_order_relaxed) * PageCache::PAGE_SIZE)
    {
        cur = getSpanTracker(current);   // 典型情况整个批次只进 1 次
    }
    if (cur)
        cur->freeCount.fetch_sub(1, std::memory_order_release);
    current = *reinterpret_cast<void**>(current);
}
```

| 项 | 值 |
|:---|:---|
| 预期收益 | 典型情况二分调用降 8 倍；跨 Span 批次退回原逻辑，无额外风险 |
| 前置条件 | **必须先修 P0-2**（僵尸 tracker 置 null），否则"复用"可能锚定在僵尸上 |
| 进阶 | 若批次内连续 N 块同 Span，可一次 `fetch_sub(N)`（省 N-1 次原子操作），收益小、复杂度增，可选 |

### 6. fetchRange 返回实际块数（省 ThreadCache 链表遍历） ✅ 已实施（2026-08-18，无单独文档）

| 项 | 值 |
|:---|:---|
| 位置 | `CentralCache.cpp:118`（签名）、`ThreadCache.cpp:137-143`（遍历计数） |
| 现状 | ThreadCache 拿回链表后自己遍历一遍数 batchNum（8 次指针解引用），而 CentralCache 在锁内已经算好 batchCount |
| 方案 | `void* fetchRange(size_t index, size_t& outBatchNum);` — 两个分支出口处 `outBatchNum = batchCount`；ThreadCache 直接用 |
| 预期收益 | 每次慢路径省一次 8 节点遍历（微小但免费） |
| 风险 | 签名变化影响所有调用点（仅 ThreadCache 一处） |

### 7. freeListSize_ / delayCounts_ 改 uint16_t（缓存足迹减半） ✅ 已实施（2026-08-18，无单独文档；边界复核：触发点 2048 + 批量 31 = 2079 < 65535 ✓，delayCounts 上限 49 ✓）

| 项 | 值 |
|:---|:---|
| 位置 | `ThreadCache.h:66`（`freeListSize_`）、`CentralCache.h:141`（`delayCounts_`） |
| 现状 | 两个 `size_t` 数组各 256KB，ThreadCache 单线程访问热数据（每次 allocate/deallocate 读写） |
| 方案 | `std::array<uint16_t, FREE_LIST_SIZE>`；`delayCounts_` 用 `std::array<std::atomic<uint16_t>, FREE_LIST_SIZE>` |
| 边界校验 | `freeListSize_` 上限 = 阈值 1024 + BATCH 32 = 1056 < 65535 ✓；`delayCounts_` 上限 = MAX_DELAY_COUNT(48)+1 ✓ |
| 预期收益 | ThreadCache 缓存足迹 512KB → 320KB，热路径命中率提升；CentralCache delayCounts_ 256KB → 64KB |
| 风险 | 阈值/BATCH 将来调大时需复核边界；`fetch_add` 在 `atomic<uint16_t>` 上语义不变 |

### 8. 归还阈值判断位掩码化（免费的小优化） ✅ 已实施（2026-08-18，无单独文档）

| 项 | 值 |
|:---|:---|
| 位置 | `ThreadCache.cpp:96-100` |
| 现状 | 每次 deallocate 都执行一次 `> 256` 比较（分支预测器已能正确预测，收益本就小） |
| 方案 | 阈值取 2 的幂（1024）后：`if ((++freeListSize_[index] & 1023) == 0 && freeListSize_[index] > 1024)` —— 每 1024 次释放才执行一次完整比较，且 `&` 运算在 `uint16_t` 上开销更低 |
| 注意 | 触发点从"首次超过阈值"推迟到"下一个 1024 整数倍"，归还略迟，可接受 |

## 五、第三档（大改、收益有限，可选）

### 9. PageCache freeSpans_ 从 std::map 改 O(1) 定长数组

| 项 | 值 |
|:---|:---|
| 位置 | `PageCache.h:77`、`PageCache.cpp:62`、`:194` |
| 现状 | `std::map<size_t, Span*>`（红黑树），每次 allocateSpan/deallocateSpan 一次 lower_bound O(log n) |
| 分析 | CentralCache 请求页数范围实际只有 1~64（≤32KB 固定 8 页，>32KB 最多 256KB/4KB=64 页）；合并后 Span 可更大（合并上限 32768 页） |
| 方案 | 若接受"合并后页数也 ≤ 1024"的上限：`std::array<Span*, 1025>` 头数组 + 每桶带头插链表，O(1)；否则 `std::unordered_map<size_t, Span*>` 保底 |
| 预期收益 | PageCache 操作频率低（每次跨层缺货才触发），收益有限；主要收益是消除红黑树开销和降低锁内时间 |
| 风险 | 改动面大；合并上限需显式约束并断言 |

### 10. 桶结构合并（链表头 + 锁同 cache line）

| 项 | 值 |
|:---|:---|
| 位置 | `CentralCache.h:118-120` |
| 现状 | `centralFreeList_[index]`（256KB）与 `locks_[index]`（4KB）相距 256KB，一次 fetch 要碰两条 cache line |
| 方案 | `struct Bucket { std::atomic<void*> head; std::atomic_flag lock; };` + `std::array<Bucket, FREE_LIST_SIZE>`（16B/桶，512KB） |
| 预期收益 | 每次桶操作少一次 cache line 访问，多线程争用下收益可感知 |
| 风险 | 数组变大 256KB；全部访问点（fetchRange/returnRange/performDelayedReturn/updateSpanFreeCount/构造函数）都要改 |

## 七、验证方法

1. **回归**：`bin/unit_test` 全绿（P0 修复后尤其要跑）；
2. **对比**：`bin/perf_test` 多线程场景为最敏感指标，取 4 轮平均（当前单轮抖动可达 ±20%）；
3. **新增场景建议**：
   - 8 线程 × 2.5 万次（放大多核争用，验证自旋锁退避）；
   - 稳态循环：同大小分配→全归还→再分配，运行数分钟观测 RSS 不增长（验证 P0-1/P0-2 修复，当前测试覆盖不到）；
4. **可选**：`perf stat -e cache-misses,context-switches` 观察缓存未命中和上下文切换是否下降（自旋锁退避的直接证据）。
