# CentralCache → ThreadCache 批量传输

## 严重程度

**性能优化 —— 跨层调用频率过高，自旋锁竞争严重**

## 位置

`src/CentralCache.cpp` `fetchRange` 分支 A + 分支 B

## 问题描述

当前 `fetchRange` 每次只返回 **1 块**，ThreadCache 每次缺块都要跨层调用：

```
当前（单块传输）:
  allocate #1 → fetchRange (持锁, 拿1块)
  allocate #2 → fetchRange (持锁, 拿1块)
  ...
  allocate #8 → fetchRange (持锁, 拿1块)
  跨层调用 = N 次，自旋锁获取/释放 = N 次

批量传输:
  allocate #1 → fetchRange (持锁, 拿8块, 7块进ThreadCache本地)
  allocate #2~8 → 命中 ThreadCache 本地 freeList_, 零跨层
  allocate #9 → fetchRange (持锁, 拿8块)
  跨层调用 ≈ N / 8 次
```

关键代码——两处都把链表断开只取头节点：

```cpp
// fetchRange 分支 B（取已有块）
*reinterpret_cast<void**>(result) = nullptr;       // 断开 head.next
centralFreeList_[index].store(next, ...);           // 剩余留在 CentralCache
return result;                                       // 只返回 1 块！

// fetchRange 分支 A（新 Span）
*reinterpret_cast<void**>(result) = nullptr;       // 同样只取 1 块
centralFreeList_[index].store(next, ...);
tracker->freeCount.store(blockNum - 1, ...);        // 减 1
return result;
```

ThreadCache 侧 `fetchFromCentralCache` 已有遍历链表、计数 `batchNum`、将剩余块放入 `freeList_` 的逻辑——但因为 `fetchRange` 永远返回单块（`next == nullptr`），`batchNum` 永远为 1，批量处理代码形同虚设。

## 影响

| 维度 | 单块传输 | 批量传输 |
|:---|:---|:---|
| 跨层调用频率 | N 次 | N / BATCH_SIZE 次 |
| 自旋锁 test_and_set/clear | 每次 allocate 都触发 | 减少 8 倍 |
| ThreadCache 本地命中率 | 低（每块用完即完） | 高（本地缓存 7 块备用） |
| 多线程锁竞争 | 严重 | 大幅缓解 |

---

## 实际修复（已应用）

### 设计思路

将 `fetchRange` 的返回值从"单块"改为"链表批次"：每次持锁后，从 `centralFreeList_` 取最多 `BATCH_SIZE(8)` 块，串成链表返回。ThreadCache 侧无需任何修改——它本来就支持接收链表。

- `BATCH_SIZE = 8`：TCMalloc 对不同大小类用不同批量，这里用统一值，简单有效
- 分支 A（新 Span）：所有块同属一个 Span，批量取走，`freeCount = blockNum - batchCount`
- 分支 B（已有块）：批次内块可能来自不同 Span（centralFreeList_ 中多 Span 的块交错），逐块查找 SpanTracker 并递减 `freeCount`

### 变更 1：头文件 `include/CentralCache.h`

```cpp
// 新增批量传输常量
static const size_t BATCH_SIZE = 8;  // fetchRange 每次批量传输块数
```

### 变更 2：分支 A — 新 Span 批量取走

**替换前：**
```cpp
// --- 从链表中取出第一块返回给 ThreadCache，其余留在 CentralCache ---
void* next = *reinterpret_cast<void**>(result);      // 保存第二块
*reinterpret_cast<void**>(result) = nullptr;          // 断开第一块
centralFreeList_[index].store(next, ...);             // 剩余挂回
// ...
tracker->freeCount.store(blockNum - 1, ...);          // 空闲 = 总数 - 1
```

**替换后：**
```cpp
// --- 批量传输：从链表头取 BATCH_SIZE 块给 ThreadCache ---
// 找出第 BATCH_SIZE 块（批次尾节点）
size_t batchCount = 1;
void* batchTail = result;
while (batchCount < BATCH_SIZE && batchCount < blockNum &&
       *reinterpret_cast<void**>(batchTail) != nullptr)
{
    batchTail = *reinterpret_cast<void**>(batchTail);
    batchCount++;
}

void* rest = *reinterpret_cast<void**>(batchTail);   // 批次后的剩余链表
*reinterpret_cast<void**>(batchTail) = nullptr;       // 在批次尾断开
centralFreeList_[index].store(rest, ...);             // 剩余挂回

// ...
tracker->freeCount.store(blockNum - batchCount, ...); // 空闲 = 总数 - 批次块数
```

### 变更 3：分支 B — 已有块批量取走

**替换前：**
```cpp
// 分支 B：中心缓存有现成的空闲块 → 取链表头
void* next = *reinterpret_cast<void**>(result);      // 保存第二块
*reinterpret_cast<void**>(result) = nullptr;          // 断开第一块
centralFreeList_[index].store(next, ...);             // 剩余挂回

SpanTracker* tracker = getSpanTracker(result);        // 找 1 块的 Span
if (tracker)
    tracker->freeCount.fetch_sub(1, ...);             // 减 1
```

**替换后：**
```cpp
// 分支 B：批量取 BATCH_SIZE 块
// 遍历找出批次尾节点
size_t batchCount = 1;
void* batchTail = result;
while (batchCount < BATCH_SIZE &&
       *reinterpret_cast<void**>(batchTail) != nullptr)
{
    batchTail = *reinterpret_cast<void**>(batchTail);
    batchCount++;
}

void* rest = *reinterpret_cast<void**>(batchTail);   // 批次后的剩余链表
*reinterpret_cast<void**>(batchTail) = nullptr;       // 断开
centralFreeList_[index].store(rest, ...);

// 批次内块可能来自不同 Span，逐块递减 freeCount
void* current = result;
for (size_t i = 0; i < batchCount; ++i)
{
    SpanTracker* tracker = getSpanTracker(current);
    if (tracker)
        tracker->freeCount.fetch_sub(1, ...);
    current = *reinterpret_cast<void**>(current);
}
```

> **为什么分支 B 逐块 getSpanTracker 不慢？**
> `getSpanTracker` 已是 O(n) 线性扫描 + 无锁原子读（Fix#3 优化）。每批次最多调用 8 次，但跨层调用次数减少了 8 倍。净效果：持锁时间虽略有增加（多取了 7 块），但锁的获取/释放频率降为 1/8，多线程下锁竞争显著减少。

### ThreadCache 侧：无需修改

`ThreadCache::fetchFromCentralCache` 已有完整的链表批量处理逻辑：

```cpp
void* ThreadCache::fetchFromCentralCache(size_t index)
{
    void* start = CentralCache::getInstance().fetchRange(index);
    // start 现在是 BATCH_SIZE 块的链表（而非单块）
    if (!start) return nullptr;

    void* result = start;
    freeList_[index] = *reinterpret_cast<void**>(start);  // 剩余 7 块进本地 freeList_

    size_t batchNum = 0;
    void* current = start;
    while (current != nullptr) { batchNum++; current = ...; }
    freeListSize_[index] += batchNum - 1;  // -1 因为 result 返回给用户

    return result;  // 返回第 1 块
}
```

`fetchRange` 返回 8 块链表 → `batchNum = 8` → 7 块进 `freeList_`，后续 7 次 `allocate` 直接本地命中。

## 压测对比

| 场景 | MemoryPool | new/delete | 结论 |
|:---|:---|:---|:---|
| SmallAllocation | 2.571 ms | 1.955 ms | ❌ 慢 31% |
| MultiThreaded | **6.443 ms** | 7.421 ms | ✅ 快 **13%** |
| MixedSizes | **2.555 ms** | 4.665 ms | ✅ 快 45% |

与 Fix#3 对比：

| 场景 | Fix#3 后 | Fix#4 后 | 变化 |
|:---|:---|:---|:---|
| SmallAllocation | 2.611 ms | 2.571 ms | −1.6% |
| MultiThreaded | 7.324 ms | **6.443 ms** | ↓ **12.0%** |
| MixedSizes | 2.496 ms | 2.555 ms | +2.4% |

> Fix#4 后 10 轮测试，`bin/perf_test`（WSL2, g++ -O2, C++17）

**结论**：MultiThreaded 改善最显著（↓12%），且首次在多线程场景下**稳定快于** `new/delete`（快 13%）。批量传输减少了 8 倍的跨层锁操作，多线程下自旋锁竞争大幅缓解。SmallAllocation 和 MixedSizes 基本持平——单线程场景下锁竞争本来就不严重，改善主要体现在多线程。
